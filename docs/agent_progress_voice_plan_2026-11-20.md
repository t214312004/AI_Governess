# Agent 進度旁白與對話框實作規劃

實作前驗證記錄於 2026-11-20（台灣時間）。愛管家在每則公開進度前加上 `嗯... `，讓使用者在同一輪對話中看到進度，也能在開啟語音輸出時聽到。前綴由愛管家處理，Agent 的提示詞、記憶注入和既有保護照原流程運作。

Codex 和 agy 已接入同一個顯示與朗讀流程。Codex 讀取原生旁白，agy 在一般對話 session 註冊 `report_progress`，由愛管家按 20 秒時點發布收到的內容。agy 是否會在普通任務中主動呼叫工具，由模型決定。

實作前的 agy 測試使用隔離的 synthetic workspace，家庭私有 context 未載入。當時這個 Windows 帳號還沒有專案管理的 `agy_acp_server.exe` 與個人 OAuth profile，因此上表的 agy 結果來自本機 `agy acp`。Windows 播放實驗觀察的是裝置回呼。

實作後先以本機 `agy acp 1.5.13` 驗證 production ACP client 和 MCP 程式。合成使用者訊息明確要求回報兩次，愛管家分別在第 20.014 秒和 40.014 秒發布進度，第 47.964 秒收到獨立的正式回答。

完成 Google AI Pro 登入後，以愛管家管理的官方 ACP `1.5.2` 重新驗收。測試使用隔離工作區及既有提示詞，只有合成使用者訊息明確要求回報。在第 20.016 秒及第 60.013 秒發布進度，第 40 秒保持安靜。兩則進度都加上 `嗯... `，對話框與 Gemini TTS 收到相同的字串，Windows 輸出裝置有播放音訊。第 96.042 秒收到獨立的正式回答，對話框收合進度，Windows 完整送出正式回答的 39,360 個 PCM samples。

未要求回報的網路查證回合到測試上限仍未完成。改用含 26 秒延遲的合成預報工具，回合於第 68.821 秒完成並正確回答星期日。全程沒有觀察到 `report_progress` 呼叫、寫入或發布。20 秒節奏控制已回報文字的發布時點，agy 是否主動產生進度仍取決於模型。

## 進度來源與格式

### Codex 原生旁白

沿用 [Codex App Server client](../ai_voice_assistant/llm/codex_cli_client.py)。依回合識別及 `itemId` 累積 `agentMessage`，旁白來源限定為明確標示 `phase: commentary` 的項目。若 delta 早於階段資訊，先暫存，等階段明確後才交付。用完成事件的全文核對已收到的文字，避免完成事件重複追加或朗讀。

UI 可隨 delta 更新同一則旁白，TTS 在項目完成後取得一次全文。正式回答和未標記階段的既有 fallback 照原本的 `send_message()` 路徑。工作進度可供活動狀態使用，正式首字的計時以正式回答的第一個文字 chunk 為準。

### agy 工具與 20 秒發布

在 [Antigravity ACP client](../ai_voice_assistant/llm/antigravity_acp_client.py) 的 `session/new` 註冊 `report_progress`。工具描述限於提交目前工作的公開進度，呼叫後立即回覆確認。用 wire-level 測試比較工具註冊前後的 `session/prompt` payload，沿用既有提示詞、記憶注入與保護。

用 monotonic clock 從送出該輪 prompt 開始計時，在第 20、40、60 秒等時點檢查暫存。每次發布目前回合最新、尚未發布的一則。時點上沒有新句就維持安靜。剛錯過時點的候選留到下一次檢查。正式回答開始、回合結束、取消或切換 session 時關閉計時器與候選。結束和發布同時抵達時，以結束優先。

正式回答沿用 `final_segment`。依目前 ACP 回覆模式，切換以愛管家真正取得正式回答文字的時間為準。agy 的進度來源只接受本輪 `report_progress`。`agent_thought_chunk` 及一般工具輸出維持原用途。沒有收到工具回報的回合，照既有流程提供正式回答。

### 共用前綴

在 [Assistant](../ai_voice_assistant/core/assistant.py) 的進度處理路徑集中加上 `嗯... `。前綴由「嗯」、三個半形句點及一個半形空格組成。若原文已經以完全相同的前綴開頭，沿用一次。空白內容略過。每則有效進度只在開頭加一次，即使包含多個句子或多個串流片段。對話框與 TTS 共用格式化結果，Agent 歷史保留原文。

## 對話框和語音

主視窗及 Session 視窗在該輪使用者訊息下方放置「處理進度」。例如 `嗯... 我先核對一下預報日期。`。進度依回合與項目更新，正式回答使用現有的助理氣泡。回合完成後收合進度，使用者仍可展開。取消時保留已顯示的內容，標示「已中斷」。靜音和純文字模式仍顯示進度。使用者向上翻閱時，維持 Session 視窗既有的捲動位置規則。參見 [主視窗](../ai_voice_assistant/ui/main_window.py) 與 [Session 視窗](../ai_voice_assistant/ui/session_window.py)。

[Gemini TTS](../ai_voice_assistant/tts/gemini_tts_engine.py) 使用現有聲線，讓每個合成工作帶自己的 `style`。進度音量稍輕、音高略低，「嗯」短而輕，換氣般短停後接續原句。正式回答維持既有語氣。旁白和回答共用現有請求限速。

初始語氣採已實測的 TTS `style`。這段文字只送給語音服務。

> 台灣華語，音量稍輕、音高略低，像工作時順口交代一句。「嗯」短而輕，停頓只像換氣，順勢接下句。整句保持連貫。逐字念出原文。

正式回答到達時，取消該輪排隊或合成中的進度，丟棄已開始播放的進度音訊剩餘 PCM，讓正式回答音訊優先。進度和正式回答共用使用者回合，播放層用個別工作識別或 generation 避免舊音訊混入。進度合成失敗只影響當次進度。全域靜音、打斷和 session 切換也應取消進度音訊。

Gemini 的 8 秒最小請求間隔以送出時間起算。取消已送出的進度合成仍可能留下等待時間，正式文字到達時，UI 立即更新。驗收分別量測正式首字、首次合成 PCM 和播放回呼首個非零 PCM。

## 實作順序與驗收

1. **先做 Codex 完整路徑。** 接上原生旁白、共用格式、對話框和語音工作。驗證多則進度、沒有進度、delta 先到、重複完成事件和只有完成事件才帶全文。核對 UI 與 TTS 使用相同文字，正式回答維持原文。
2. **驗收真實語音切換。** 用 Gemini API 和 Windows 輸出確認「嗯」確實被念出、停頓自然。測試答案在旁白排隊、合成中與正在播放時抵達，核對沒有舊旁白混入。驗證靜音、使用者打斷和 session 切換，並比較開關功能前後的正式回答首音。
3. **在專案管理的 ACP runtime 驗收 agy。** 沿用既有提示詞跑自然的長任務，記錄工具發現、主動呼叫及實際發布時間。另以合成使用者訊息明確呼叫工具，驗收 20 秒發布和語音。沒有工具回報的回合，照常提供正式回答。
4. **做跨入口回歸。** 驗證語音輸入、文字輸入搭配語音輸出、純文字與兩種視窗。用 fake clock 驗證時間邊界、暫存被取代、無候選和取消同時發生。比對註冊前後的 prompt bytes，並確認未改動既有權限與輸出檢查。
